     3→Project: Garment Broker OS — a glassmorphic, finance-grade operations system for a garment industry broker.
     4→Source plan: `/home/z/my-project/upload/broker-os-plan.md`
     5→
     6→Architectural analysis (summary):
     7→- Database: PostgreSQL recommended in plan, but sandbox uses SQLite via Prisma — fully sufficient for v1 single-broker; schema is portable to Postgres with zero model changes.
     8→- Photos: local FS under `public/uploads/` + `Photo` model (stage-polymorphic). S3-migrable.
     9→- Audit log: append-only `AuditLog` table for every financial mutation (payments, billing adjustments, brokerage) — required for dispute resolution.
    10→- Brokerage payout: added `BrokeragePayout` entity to group eligible brokerages into a batch (immediate / 4-month / 12-month cadence), per-client.
    11→- Computed fields (fulfillment %, credit exposure, avg delay): computed on-read via Prisma aggregations, never stored.
    12→- Open questions (§13) resolved with sensible defaults: one PO per visit-supplier pair; GST configurable per supplier with system default; returns logged separately but feed supplier reliability score; cumulative window = rolling from first eligible payment; manual `forceEligible` override on Brokerage with reason + audit.
    13→- UI: glassmorphism, emerald accent (avoiding indigo per design rules), dark mode first-class via next-themes, sidebar shell.
    14→- Stack: Next.js 16 App Router, TypeScript, Tailwind 4, shadcn/ui, Prisma (SQLite), Zustand, TanStack Query, recharts.

   719→  - Fulfillment (40% wt): avg of `min(1, dispatchedQty/orderedQty)`; empty → 100. `totalSupplied` ≈ `po.totalValue × share`.
   720→  - On-time dispatch (30% wt): `% of dispatches where dispatchDate <= (revisedDispatchDate ?? expectedDispatchDate)`; only counts dispatches with an expected date; empty → 100.
   721→  - Low short-shipment (20% wt): `100 - shortShipmentRate%` (% not `short_shipment`).
   722→  - Low dispute rate (10% wt): `100 - (disputes on their POs / total POs × 100)`.
   723→  - Composite = `0.4×F + 0.3×OT + 0.2×(100-SS) + 0.1×(100-D)`, clamped [0,100].
   724→  - Tier: ≥85 excellent, ≥70 good, ≥55 average, <55 needs attention.
   725→  - Sorted by score desc. Returns `{ supplierId, name, score, fulfillment, onTimeRate, shortShipmentRate, disputeRate, dispatchCount, totalSupplied, tier }[]`.
   726→
   727→**b) Client credit exposure** — per client:
   728→  - Outstanding: `sum(finalAmount - paidAmount)`.
   729→  - Exposure trend (6 monthly buckets): outstanding snapshot at month end — `sum(finalAmount - paidAmount)` for bills where `createdAt <= monthEnd` (uses current paidAmount; per spec's "approximate" note).
   730→  - Avg payment delay (days): for fully-paid bills, `avg(lastPaymentDate - bill.createdAt)`; ignores negative outliers.
   731→  - Return rate: `defective_return disputes on client's POs / total bills × 100`.
   732→  - Sorted by outstanding desc. Returns `{ clientId, name, outstanding, exposureTrend: [{month, value}], avgPaymentDelay, returnRate, billCount }[]`.
   733→
   734→**c) Brokerage forecast**:
   735→  - pendingTotal: sum where `eligible=false`.
   736→  - eligibleUnpaidTotal: sum where `eligible=true && payoutStatus != "paid"`.
   737→  - byCadence: groups eligible-unpaid by client's `payoutCadence` → `{ immediate, 4_month, 12_month }`.
   738→  - projectedByMonth (next 3 months): immediate → 100% in month 0; 4_month → 1/4 each month for 4 months; 12_month → 1/12 each month for 12 months. Summed per month, rounded.
   739→  - Returns `{ pendingTotal, eligibleUnpaidTotal, projectedByMonth: [{month, amount}], byCadence }`.

   742→  - monthlyBilled (12 monthly buckets): sum of `bill.finalAmount` by createdAt.

  1942→## 2. /api/digest route (new)
  1943→- Created `/home/z/my-project/src/app/api/digest/route.ts`.
  1944→- `GET /api/digest?format=text|html|email` — single Prisma pass to gather all digest data, then format-specific rendering.
  1945→- **Data gathered** (one `Promise.all` of 6 Prisma queries):
  1946→  - Visits with `status in [scheduled, followed_up]` and `plannedDate ≤ now + 3d` (action items + upcoming)
  1947→  - Open POs with `expectedDispatchDate < now` (overdue dispatches)
  1948→  - Bills not `fully_paid` with client's `defaultPaymentCycleDays` (outstanding receivables + payments due next 7d + top 3 clients by due)
  1949→  - Eligible brokerages with `payoutStatus in [accrued, scheduled]` (brokerage pending payout, aggregated per client)
  1950→  - Open disputes (count + list)
  1951→  - Pending notifications (count)
  1952→- **Action items** (simplified from /api/action-center): visit follow-ups (urgent if >2d overdue), overdue dispatches (always high), payment due (urgent if >14d past, high if past, normal if due ≤7d), brokerage payout (high), dispute resolve (urgent if >7d open, else high). Sorted by priority asc then dueDate asc, capped at 12.
  1953→- **format=text**: plain-text digest with KPI summary, prioritised actions, outstanding receivables (top 3 clients), overdue dispatches, payments due next 7d, brokerage pending payout (accrued/scheduled/total), open disputes count.

Email-client-friendly (table-based layout, inline styles, no external CSS, web-safe font stack).

Builds a compact JSON data summary (top 6 actions, top 3 clients with due, top 4 overdue dispatches, top 4 payments due, brokerage totals), then calls the LLM with a system prompt: "You are a concise, professional assistant briefing a garment broker on their day. Summarize the key actions needed today based on the data. Be specific with names and amounts. Keep it under 200 words. Use Indian Rupee formatting (e.g. ₹1,25,000). Start with a one-line greeting that includes the date." Returns `{ subject, body, aiGenerated }` where subject is "Broker OS Daily Digest — {date}".
