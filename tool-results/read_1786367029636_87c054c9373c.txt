     4→     4→Source plan: `/home/z/my-project/upload/broker-os-plan.md`
     5→     5→
     6→     6→Architectural analysis (summary):
     7→     7→- Database: PostgreSQL recommended in plan, but sandbox uses SQLite via Prisma — fully sufficient for v1 single-broker; schema is portable to Postgres with zero model changes.
     8→     8→- Photos: local FS under `public/uploads/` + `Photo` model (stage-polymorphic). S3-migrable.
     9→     9→- Audit log: append-only `AuditLog` table for every financial mutation (payments, billing adjustments, brokerage) — required for dispute resolution.
    10→    10→- Brokerage payout: added `BrokeragePayout` entity to group eligible brokerages into a batch (immediate / 4-month / 12-month cadence), per-client.
    11→    11→- Computed fields (fulfillment %, credit exposure, avg delay): computed on-read via Prisma aggregations, never stored.
    12→    12→- Open questions (§13) resolved with sensible defaults: one PO per visit-supplier pair; GST configurable per supplier with system default; returns logged separately but feed supplier reliability score; cumulative window = rolling from first eligible payment; manual `forceEligible` override on Brokerage with reason + audit.
    13→    13→- UI: glassmorphism, emerald accent (avoiding indigo per design rules), dark mode first-class via next-themes, sidebar shell.
    14→    14→- Stack: Next.js 16 App Router, TypeScript, Tailwind 4, shadcn/ui, Prisma (SQLite), Zustand, TanStack Query, recharts.
